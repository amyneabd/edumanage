# French Localization — Design Spec

**Goal:** Translate every piece of client-visible text in the app to French, in place, with no language toggle. The app becomes French-only.

**Status:** Approved by user in brainstorming session 2026-09-05. Ready for implementation planning.

## 1. Principle & Boundary

One rule governs the entire effort: **if a client/user can see it, it becomes French. If it's internal-only, it stays English.**

**Translated (in scope):**
- All client UI copy: labels, buttons, nav items, headings, empty states, toasts, tooltips, aria-labels, alt text.
- Client-side form validation messages (e.g. Zod schema `.message()` strings in `authSchemas.ts`).
- Server error messages that get returned to and displayed by the client (thrown `Error` subclasses like `AuthError`, `SwapError`, and any inline error strings in controllers).
- Notification titles/bodies generated by `notification.service.ts` (the static template text — embedded user names, dates, and other data values are not translated, see §5).
- Both email templates in `mailer.ts` (password reset, email verification) — subject, plain-text body, and HTML body.
- Date/time display conventions (see §4).
- Test assertions that check any of the above (a task isn't done until its own tests pass against the French text).

**Never translated (out of scope):**
- User-generated content: names, class names, post/exam content, anything a user typed into a form.
- Code comments, console/log output (`console.warn`, `console.error`, etc.), dev/seed/QA scripts (the `server/*.mjs` utility scripts).
- Database enum values, field names, Prisma schema, API JSON keys, git history, commit messages.
- The application/brand name ("Bachandi").

## 3. Centralization (do this before per-page translation)

Several labels are currently duplicated inline across multiple files instead of defined once. Centralizing first means the per-page translation work is a mechanical "import the shared label" edit, and there's one place to get each translation right instead of five.

- **New file `client/src/lib/labels.ts`:** exports one lookup object per enum in §2's status table (`CLASS_TYPE_LABELS`, `PAYMENT_STATUS_LABELS`, `USER_STATUS_LABELS`, `ROLE_LABELS`, `SWAP_REQUEST_STATUS_LABELS`, `PARENT_LINK_STATUS_LABELS`, `ATTENDANCE_DISPLAY_LABELS`), each typed against the corresponding union type in `client/src/api/types.ts`. Every file currently inlining one of these maps (`TeacherDetailPage.tsx`, `FeedPage.tsx` in teacher/pupil/parent, `HomePage.tsx` in pupil/parent, `LedgerPage.tsx`, etc.) switches to importing from here instead.
- **`client/src/lib/period.ts`:** `DAY_NAMES` becomes the French array from §2. `formatPeriodLabel` passes `"fr-FR"` instead of `undefined` as the locale argument. A new exported `formatDate(value: string | Date, options?: Intl.DateTimeFormatOptions): string` wraps `new Date(value).toLocaleDateString("fr-FR", options)`.
- All ~15 bare `new Date(...).toLocaleDateString()` call sites (admin/parent/pupil pages — `AdminPage.tsx`, `TeacherDetailPage.tsx`, `FeedPage.tsx` ×2, `GradesPage.tsx` ×2, `HomePage.tsx` ×2, `LedgerPage.tsx`, `PaymentsPage.tsx` ×2) switch to calling the new `formatDate()` helper instead of calling `toLocaleDateString()` directly, so the locale is enforced in one place.

## 4. Date/time formatting

- Day names: French abbreviations per §2.
- Written dates: French convention via `formatDate()` (`"fr-FR"` locale), e.g. `5 sept. 2026` (short) or `5 septembre 2026` (long, matching each call site's existing `options` — `formatPeriodLabel` keeps its `{ month: "long", year: "numeric" }` shape, now rendering e.g. `septembre 2026`).
- Schedule times (`"16:00"` style strings from `ScheduleSlot.startTime`/`endTime`) are stored and displayed as raw 24-hour `HH:mm` strings already — no change needed, this format reads naturally in French.
- Locale is hardcoded to `"fr-FR"`, not derived from the browser — the app must look French regardless of the visiting user's OS/browser locale.

## 5. Server-side scope

**Client-visible error messages** — every `throw new XError("...", status)` (or plain `Error`) whose message reaches the client via the JSON error response, across the service layer (`auth.service.ts`, `swap.service.ts`, `attendance.service.ts`, `payment.service.ts`, `class.service.ts`, `parent.service.ts`, `admin.service.ts`, and their controllers) gets its message text translated to French. Internal-only errors that never reach a client response (e.g. a thrown error that's caught and logged, never serialized to the caller) stay in English.

**Notifications** (`notification.service.ts`) — the static template portions of `title`/`body` translate; embedded dynamic values (a pupil's name, a period string, an exam's content snippet) are not touched — they're user data, not app copy. Example: `"Payment overdue"` → `"Paiement en retard"`; `` `${record.pupil.user.name}'s payment for ${record.period} is ${overdue ? "overdue" : "due today"}.` `` → `` `Le paiement de ${record.pupil.user.name} pour ${record.period} est ${overdue ? "en retard" : "dû aujourd'hui"}.` ``.

**Emails** (`mailer.ts`) — both `sendPasswordResetEmail` and `sendVerificationEmail` (subject, `text`, and `html` fields) translate fully. The generic notification-email helper's wrapping markup (`<p>${body}</p>...View details...`) translates its static parts; `body` itself arrives already-translated from the notification service.

## 6. Client-side scope

Every file under `client/src/features/{account,admin,auth,parent,pupil,teacher}/`, shared components (`AppLayout.tsx` nav, `Badge.tsx`, `NotificationBell.tsx`, `Pagination.tsx`, modals like `PupilDetailModal.tsx`, `PupilContactModal.tsx`, `PupilLedgerModal.tsx`), and `client/src/lib/authSchemas.ts` validation messages. This includes:
- Static JSX text (headings, labels, button text, empty-state copy, hint text).
- `aria-label` and `alt` attributes.
- Toast/alert messages surfaced from API error responses are already covered by §5 (they render the server's message directly) — no separate client-side translation needed for those, only for client-originated copy (e.g. "Loading...", "No results found.").

## 7. Testing strategy

No separate translation-then-fix-tests pass. Each implementation task translates its file(s) **and** updates every test assertion in the corresponding test file(s) that checks the old English text, in the same commit. This applies to:
- Client: `getByText(...)`, `getByRole(..., { name: ... })`, and any literal-string assertions across the ~11 client test files (~27 call sites currently).
- Server: `expect(error.message).toBe("...")` / `.toThrow("...")` style assertions across the ~12 server test files wherever the underlying service message changed.

A task is not complete if its tests still assert English text for strings the task translated.

## 8. Non-goals

- No i18n library (react-i18next, next-intl, etc.) and no language-switching UI. The app is French-only after this change; reintroducing English later is a new, separately-scoped project.
- No translation of user-generated data under any circumstance, even if it happens to be in English.
- No changes to database enum values, Prisma schema, or API request/response JSON key names — only the human-readable label text derived from those values changes.
- No changes to dev/seed/QA scripts (`server/*.mjs`), code comments, or logging output.
- No systematic pluralization algorithm — each string with a count-dependent form (e.g. "1 pupil" / "2 pupils") is translated by hand for its specific words (French pluralizes `élève`/`classe`/`paiement` etc. with a simple `s`, same shape as the existing English pattern), not by a shared utility.

## 9. Execution

Implemented as a single implementation plan (one cohesive goal, not independent subsystems) executed via subagent-driven-development, matching the process used for the swap-request feature. Tasks are batched by feature directory (e.g. all of `features/pupil/*` as one batch) rather than one subagent per file, since the edits are the same shape repeated. Centralization (§3) happens in early tasks so later per-page tasks can simply import shared labels instead of re-deciding translations.
